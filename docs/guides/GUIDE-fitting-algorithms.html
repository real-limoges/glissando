glissando · fitting algorithms: CG & grid λ

Implements FIT-3 (the CG / Cole-Green algorithm, gamlss's second fitter, for cross-parameter derivative coupling when RS mixes slowly) and FIT-4 (grid / "magic"-style smoothing-parameter selection as an alternative to the L-BFGS criteria). Both are alternatives bolted alongside the current machinery and selected by config; neither rewrites the working RS path.

Current state. fit_gamlss (src/fitting/mod.rs:332) is RS-only: its outer loop (mod.rs:415+) cycles, and the inner loop (mod.rs:432) walks for param_name in family.parameters(), fitting each distribution parameter's predictor one at a time, treating the others as fixed. The smoothing parameters λ are chosen inside the scoring step by SmoothingCriterion (mod.rs:58) dispatching (scoring.rs:220–226) into the L-BFGS optimizers (solver.rs:278/:337) or the Fellner-Schall fixed point (solver.rs:400). FIT-3 changes the first loop; FIT-4 adds a fourth criterion.

FIT-3 · CG (Cole-Green) algorithm

RS is block-coordinate ascent: it updates μ's predictor holding σ, ν fixed, then σ holding the rest fixed, and so on. That is fast and stable when the parameters are near-orthogonal, but mixes slowly when they are strongly correlated (the heavy-tailed / skew families). CG instead forms the full cross-parameter expected-information system (the off-diagonal ∂²ℓ/∂η_p∂η_q blocks RS throws away) and updates all predictors jointly each cycle.

There is no algorithm enum today; RS is hardcoded. Introduce one and dispatch on it.

  1. The algorithm enum, in src/fitting/mod.rs (near the SmoothingCriterion definition, ~mod.rs:70): 
    #[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
#[cfg_attr(feature = "serde", derive(serde::Serialize, serde::Deserialize))]
#[cfg_attr(feature = "serde", serde(rename_all = "snake_case"))]
pub enum FittingAlgorithm {
    /// Rigby–Stasinopoulos block-coordinate ascent (current behaviour).
    #[default]
    RS,
    /// Cole–Green: joint update using cross-parameter expected information.
    CG,
}
  2. The config field: add to FitConfig (mod.rs:89–123), mirroring how criterion is declared so it round-trips through serde: 
    /// Fitting algorithm: RS (default) or CG for coupled parameters (FIT-3).
#[cfg_attr(feature = "serde", serde(default))]
pub algorithm: FittingAlgorithm,
    Add a with_algorithm builder next to with_na_action (mod.rs:128) and seed the field in Default for FitConfig.
  3. The dispatch: branch once in fit_gamlss's outer loop body (~mod.rs:428), before the per-parameter walk: 
    match config.algorithm {
    FittingAlgorithm::RS => {
        for param_name in family.parameters() {
            // …existing one-at-a-time scoring step (unchanged)…
        }
    }
    FittingAlgorithm::CG => step_cg(&mut state, family, data, config)?,
}
  4. The coupled step: a new step_cg beside scoring.rs::step (scoring.rs:126). Where step builds the working response and weight for one parameter from its diagonal Fisher block, step_cg assembles the stacked system across all parameters and solves it once: 
    // Per cycle, for parameters p = 1..P with predictors η_p = X_p β_p:
//   • working response z_p and diagonal weight W_pp as in RS (scoring.rs::step)
//   • PLUS the off-diagonal weights W_pq = −E[∂²ℓ / ∂η_p ∂η_q]   (RS sets these 0)
// Solve the block system  (Xᵀ W X + S) β = Xᵀ W z  for the *stacked* β,
// where W is the P·n × P·n expected-information matrix (block-tridiagonal in
// practice), X = blkdiag(X_p), S = blkdiag(λ_p S_p). Reuse fit_pwls
// (solver.rs:463) on the assembled blocks; the only new code is the
// cross-parameter weight blocks, which come from the family's derivatives.
    The off-diagonal weights need the family to expose its mixed second derivatives; most two-parameter families have a closed form (e.g. Gaussian's ∂²ℓ/∂η_μ∂η_σ), and where it is awkward the numeric cross-derivative is a fallback.

Validate: on well-conditioned data RS and CG must converge to the same coefficients (to tolerance); that is the regression test. The win shows on a deliberately correlated fit (e.g. a heavy-tailed family where RS needs many cycles): CG reaches the same deviance in markedly fewer. Oracle: R gamlss(..., method = CG()).

FIT-4 · Grid / "magic" λ selection

The L-BFGS optimizers minimize REML/GCV by gradient descent in log λ: fast, but able to stall in a local minimum or on a flat ridge. A grid search over log λ is the robust fallback (mgcv's "magic"/"performance iteration" lineage): evaluate the same criterion the L-BFGS path uses on a coarse log-spaced grid, take the minimizer, optionally golden-section-refine around it. It is a new SmoothingCriterion value, so it slots into the existing dispatch with no change to the RS loop.

  1. The variant: extend SmoothingCriterion (mod.rs:58–66): 
    pub enum SmoothingCriterion {
    Gcv,
    #[default]
    Reml,
    FellnerSchall,
    /// Grid search over log λ minimizing the GCV/REML score (FIT-4).
    Grid,
}
    Optionally carry grid resolution on FitConfig (default to a sensible span/step) rather than hardcoding: 
    /// log10(λ) grid bounds and point count for `SmoothingCriterion::Grid` (FIT-4).
#[cfg_attr(feature = "serde", serde(default = "default_lambda_grid"))]
pub lambda_grid: (f64, f64, usize),   // (log10_lo, log10_hi, n_points)
  2. The dispatch arm: in the criterion match (scoring.rs:220–226), route Grid to a new optimizer: 
    match config.criterion {
    SmoothingCriterion::Gcv => run_optimization(/* GCV target */ …),
    SmoothingCriterion::Reml => run_optimization_reml(…),
    SmoothingCriterion::FellnerSchall => run_optimization_fellner_schall(…),
    SmoothingCriterion::Grid => run_optimization_grid(…, config.lambda_grid),

Validate: on a smooth where the L-BFGS criterion has a clean unimodal score, Grid and Reml/Gcv pick the same λ (to grid resolution) and the same EDF. The value case is a pathological score surface where L-BFGS undersmooths; grid finds the global minimum the gradient method walked past. Surfacing & diagnostics

Both items are config-only from the caller's view, so the cross-surface work is small: thread algorithm / criterion: "grid" through the JSON FitConfig shape (src/json.rs), which serde already covers once the enums derive Serialize/Deserialize, and through the Python FitConfig wrapper (src/python.rs). Record which algorithm/criterion actually ran in FitDiagnostics (mod.rs:188–217) so a fit is reproducible from its own report; the existing final_deviance field already lets a test assert RS-vs-CG agreement.
