glissando · data & formula ergonomics

Implements DATA-1…DATA-5 — offsets, factor / contrast encoding, interactions, NA handling, and a string formula parser. The biggest usability lever in the roadmap: today users pre-expand factors by hand and build formulas from raw enum struct-literals. Ordered below from lowest-risk to highest so each step ships independently.

Touches three layers: the Term enum (src/terms.rs), the assembler that turns terms into columns (src/fitting/assembler.rs), and — for the parser — a thin front-end over Formula (src/types/formula.rs). Everything downstream of Vec<Term> stays unchanged.

What exists today

DataSet is HashMap<String, Array1<f64>> — all columns are f64; categoricals are pre-expanded by the user. Formula is HashMap<String, Vec<Term>> built via with_terms / add_terms (src/types/formula.rs:35–43). Term is Intercept | Linear{col_name} | Smooth(..). The assembler reads columns through get_col (assembler.rs:17) and records per-term layout (TermLayout: n_coeffs, null_dim, is_smooth — assembler.rs:30). It already imports two primitives you will reuse: sum_to_zero_basis and row_kronecker_into (assembler.rs:7–11).

Build order — lowest risk first

  1. DATA-3 · Offsets smallest
    A known per-row term that enters η additively with a fixed coefficient of 1 (e.g. log(exposure) for rate models). Add Term::Offset{ col_name }; in the assembler emit it with n_coeffs = 0, null_dim = 0, is_smooth = false — it contributes to η, not to β, so it needs a small carry-through into the predictor assembly rather than a design column. Verify by hand-computing η = Xβ + offset on a tiny case.
  2. DATA-1 · Factors / contrast encoding
    A categorical column that the assembler expands into dummy columns under a chosen contrast (treatment vs sum-to-zero). Add Term::Factor{ col_name, contrast }; expansion lives entirely in the assembler. Reuse sum_to_zero_basis (already imported, assembler.rs:7–11) for the sum-to-zero contrast so a factor sharing a parameter with the Intercept stays identifiable. Set n_coeffs = levels − 1. Decide how levels are carried: a small companion map on DataSet, or a convention that integer-coded columns are factors when wrapped in Term::Factor.
  3. DATA-2 · Interactions (x:z, x*z)
    Row-wise products of two terms' columns. x:z is the product block; x*z expands to x + z + x:z. The right primitive is row_kronecker_into (already imported, assembler.rs:9) — the same row-Kronecker used for tensor smooths. Add an interaction Term variant carrying the two operands; n_coeffs is the product of the operands' column counts. Factor×continuous and factor×factor both fall out of the same product once DATA-1 exists.
  4. DATA-4 · NA / missing-data handling
    Today validate_inputs rejects any non-finite value. Add an na_action on FitConfig (default: drop-rows, like R's na.omit; plus a documented imputation hook). Apply the row mask once, upstream of assembly, consistently to y, weights, and every data column — so X, z, and W all align. Keep the existing reject-path available as na.fail.
  5. DATA-5 · String formula parser highest value
    Parse "y ~ s(x) + z + f:g" into the same Vec<Term> the builder produces — a thin front-end over Formula/Term so nothing downstream changes. Grammar: response ~ sum of terms; s(x) → Smooth(PSpline1D) with optional k=/bs= args mapping to the existing builder knobs, te(x,z) → tensor, bare name → Linear, 1/implicit → Intercept, :/* → the DATA-2 variants, offset(e) → DATA-3. Overlaps API-1 (fluent builder) — note the shared Term target so the two front-ends converge.

Tests & reference oracle

  • Parser round-trips TEST-1: proptest string → Formula → string idempotence over generated formulas; reject-cases for malformed input.
  • Design-matrix snapshots TEST-4: insta golden snapshots of the assembled columns for a factor, an interaction, and x*z — the cheapest way to lock contrast encoding.
  • Offset correctness: a fit with a known offset matches a fit where the offset is folded into y by hand (closed-form η check).
  • NA handling: drop-rows produces the same fit as manually pre-filtering the data; na.fail still errors.

External oracle: R model.matrix(~ f + x:z, data) for factor / interaction / contrast columns (treatment contrasts are R's default; contr.sum for sum-to-zero). The string-formula grammar should accept the R/mgcv spelling so the migration guide (DOC-4) is a straight translation.

Cross-surface bindings BIND-3

The string parser is the highest-value cross-surface win — once it exists, expose it in the JSON facade (src/json.rs parse_formula), WASM (src/wasm.rs), and Python (src/python.rs) so all four surfaces accept "y ~ s(x) + z" instead of hand-built term JSON. Factor and offset support must also thread through the JSON parse_data / parse_formula path so a serialized model carries factor metadata. Python especially benefits: a pandas DataFrame with categorical dtypes (BIND-2) maps naturally onto DATA-1 factors.
